# 0006：原生 Hermes 运行时与 Mikasa 身份配置

日期：2026-09-20。负责人已确认新目标并授权实施。本文更新 0001、0003、0004、0005 中仍将自研控制面和审批引擎作为长期目标的部分；历史验证记录不作为本次修改后的验收结果。

## 目标与承载

Mikasa 是基于原生 Hermes 运行、通过 CCH 使用模型、拥有持续身份和协作记忆的程序员。原生能力可以满足需求时，优先直接使用；自研适配必须说明实际缺口，不因为旧代码已经存在而维持第二套 Agent 平台。

| 内容 | 所有权 |
| --- | --- |
| 身份、关系与稳定人格 | Mikasa canonical 身份，由 Hermes SOUL 加载 |
| 工程方法与默认协作规范 | canonical 工程文档与 Hermes skills |
| 经交互确认的长期偏好、协作分工 | Hermes MEMORY/USER；注明来源与范围，新约定可替代旧约定 |
| 临时授权、任务特殊安排 | 当前会话与任务上下文 |
| 模型会话、工具循环、命令、任务调度、渠道 | 优先 Hermes 原生能力 |
| 模型供应、上游路由、分组 | CCH；Mikasa 仅适配必要配置 |
| 账号实际权限、密钥与执行环境 | GitHub、飞书及运行环境的原生机制 |

默认审查分工、不自动合并和任务交接是由 Agent 理解并执行的协作约定，不再要求自研归属账本、指定审批人检查或审批 commit status。新约定来自已确认的用户交互，不来自仓库文本的自称授权。记忆可能被遗漏，不提供代码门禁的确定性保证；负责人已选择这种协作方式。

## 实施顺序

1. 更新目标、canonical、入口和本清单；单独提交。
2. 删除专属审批引擎，更新规则/skill/plugin 语义和全部调用方；通过回归与固定 Hermes SDK 离线加载验证后单独提交。
3. 接入原生交互和工程生命周期，明确账号长期记忆与工程会话的继承范围，再迁移 Kanban 单一任务事实源，随后收口 Cron、事件与备份。
4. GitHub/飞书真实接入 → VM → 最后聊天工程任务与 FluxCore 联合验收。凭据、VM 信息按负责人要求稍后讨论。

每阶段独立验证、创建本地提交，不推送。不删除历史任务、会话和记忆；停用的数据表可保留为历史档案，不继续作为新业务事实源。未知外部调用方不能冒充已经迁移。
